# RFD0003 — A reusable GitHub source and instance host

- Status: In progress on feature branches (no host cutover, no live auto-merge)
- Pilot instance: `leostera/r4` on the existing `r4` and `r4-coder-runtime` Workers
- Related: [RFD0002](RFD0002-clankwerk-cloudflare-native.md), [GitHub workflows](../github-workflows.md)

## Boundary

A Clankwerk project should **declare** GitHub event sources and workflows, supply secret bindings and repository-specific authorization, and deploy one instance Worker. Enabling another installed repository must be an **operator data change, not a source edit or deployment**. It should not implement another webhook parser, scheduler, run index, retry loop, or GitHub publication protocol. Clankwerk is a _library bundled into that instance Worker_, not a second hosted control plane or one Worker per workflow. The existing GitHub trigger/dispatch/scheduler primitives are a starting point, not yet a plug-and-play host: the template still owns routing and projection, and R4 still runs its own scheduler and admission code.

The host must be composable: non-GitHub/manual/cron sources can share the same runtime. A GitHub plugin must not force every user to install a GitHub App or bundle GitHub secrets in graph manifests. Authenticated event data is still untrusted task input. Host-specific policy remains in host-supplied capabilities or workflow tasks.

## Multi-repository enablement and isolation

An App installation and event subscription establish _transport and potential permission_, not consent to automate every installed repository. An operator uses an Access-protected registry to opt in each repository and select which workflows are enabled. The registry validates the installation and least required permissions on enable and again before credential-bearing effects; disabling a repository stops new activations **and subsequent writes from in-flight runs**. Persist normalized `owner/repo`, GitHub's immutable repository ID, installation identity, base-branch/policy, workflow toggles, and revision—not a token. Match both repository ID and current owner/name at admission and before writes; a rename or transfer requires an explicit revalidation, never implicit authorization of a different repo now using the old name. A repo is disabled by default, and only a server-authorized operator may change this registry (with an audit record). The protected API must list App-installed repositories and offer enable/update/disable operations: enable verifies immutable ID, installation, required permissions and base branch; policy explicitly selects workflows and label/issue eligibility. A failed verification leaves the repo disabled. Use an authoritative, revisioned registry for admission and effect guards; an eventually consistent D1 dashboard projection is **not** an authorization source. Disabling must prevent new GitHub write calls after its acknowledgement; a call already in flight cannot be undone. Secrets stay in Worker bindings or trusted credential DOs. App `issues` and `pull_request` subscriptions are a prerequisite for automatic delivery from newly installed repositories; the existing R4-only repository hook cannot provide this.

Every activation, run ID, durable queue partition, idempotency key, agent/workspace instance, review receipt and Check Run external ID includes the authenticated repository identity. Distinct repositories may both have issue #1 and a PR at the same head SHA without sharing state. Each App token must be minted for exactly the active `owner/repo`; the credential boundary must verify that GitHub granted the required App permissions and that the enabled repository still belongs to the pinned installation. The signed webhook payload does not itself grant permission. The current R4 defaults (`main`, `r4/issue-*`, issue #12+, labels and Bun lockfile cache) are **not generic defaults**: obtain a repo's configured/default base branch, validate labels and test strategy per repo, and report blocked evidence when a repository is unsupported. A generic source must not silently grant review/write access to forks or an unconfigured repo.

End-to-end acceptance requires enabling a second installed repo **without a Worker deploy**, opening its issue #1 and PR, and observing its own label/draft/review/checks without touching R4 issue #1 or its workspaces. This requires an App installed on that repository and subscribed to the relevant events, with the required GitHub permissions; it is not a promise to automate arbitrary repositories without consent or access. A disabled repo must produce no run or write. Cover revocation during a running job, duplicate deliveries across the old repository hook and App hook, and stale PR heads. Preview must use isolated Workers/DOs/D1 and a protected admin hostname; do not subscribe the production App or forward the production hook before explicit cutover.

## Proposed public seams (illustrative, not final signatures)

1. **Source declaration:** `githubAppSource({ path, secret: env => env.GITHUB_APP_WEBHOOK_SECRET, enabledRepositories: registry, events: [...] })` returns typed `issue.opened`, `issue.reopened`, and `pull.opened/reopened/synchronize` graph triggers with deterministic IDs for **any enabled installed repository**. Fixed-repository hooks remain optional for migration, but are not the primary multi-repository interface. A secret resolver is called at request time; neither secret nor token enters manifests, logs, persisted events, client bundles, or sandbox tools. Multiple paths/secrets (repository and App hooks) may target one logical source.
2. **Authenticated admission:** an instance-host adapter accepts a trigger-host request, bounds its raw bytes, verifies the correct HMAC before JSON decoding or _any_ activation, validates action and normalized owner/repository against an **Access-protected, durable enabled-repository registry**, computes a repository-qualified stable key, and durably claims/queues events before responding 202. Invalid/unrecognized deliveries return an explicit 4xx/204; unavailable storage returns 503 for GitHub retry. Shared-path triggers authenticate the request once against the correct path's secret, not one verification per workflow or an OR across unrelated secrets. An unexpected host/path cannot reach admin routes.
3. **Execution:** a Clankwerk-provided run coordinator (`WorkflowScheduler`, `durableObjectRunStore`, and, for partitions, `WorkflowQueue`) owns step transitions, fan-out/join, leases, retries, alarms, and compatible-definition checks. The instance registers workflows and injects environment-bound capabilities; it does **not** copy the phase machine. Keep run DOs and worker routing within the instance's existing Worker. Provide a generic D1 projection/index and read-only dashboard API adapter with optional host routes, so a new instance does not hand-write schema/metrics/runs/source endpoints. HTTP adapter must enforce the admin/trigger hostname split; Access is verified by the instance deployment, never bypassed by a public path.
4. **GitHub effects:** reusable dynamically repository-scoped App installation tokens, current-issue reads and reconciled label/comment writes, bounded archives/read-only Git gateway, exact-head PR validation, bounded diffs, idempotent draft/review publication, and individually reconciled Check Runs. `checks:write` is optional and explicit. Verify GitHub's current PR head immediately before every review/check write. A blocked dimension never counts as success. An App bot cannot approve or request changes on its own PR; do not fabricate approval. Publishing a draft/review/check has no merge effect. A separate, explicitly enabled auto-merge workflow may request **GitHub native auto-merge** only under the policy and live gates below; never call a direct merge endpoint or bypass branch protection. No credential enters a Coder container or Pi tool.
5. **Instance extension points:** enabled-repository policies (base branch, allowed workflows, issue eligibility), model/agent definitions, source-specific workspace, offline dependency strategy, prompts, and human-merge rules stay in the instance. Clankwerk owns the generic configuration storage and GitHub verification; R4 supplies its **defaults and domain policy**, not a compile-time repository allowlist. R4's #12+ feature gate must not apply to issue #1 of a newly enabled repository. Package a Cloudflare sandbox adapter only where it is reusable; R4's Docker image, Bun lockfile cache and concrete application policy are not generic Clankwerk runtime concerns.

Avoid a broad `createApp()` that silently provisions DNS/Access, merges PRs, grants webhook permissions, or guesses a secret. Typed config and explicit capabilities are preferable to a generic `Env`/`any` escape hatch. Preserve the `cf` deployment flow.

## Current code seams (why extraction alone does not satisfy this RFD)

- `packages/clankwerk/src/connectors/github-trigger.ts` requires a compile-time `repository`, and its source key namespaces by that slug. `runtime/webhook.ts` currently replays one body to each matching graph trigger and calls `verify` for each. Neither is an App-wide, single-verification enabled-repository admission boundary.
- `connectors/github-app.ts` already mints a **single-repository** installation token, and now supports pinning the numeric repository ID, but R4 has not yet supplied a runtime policy or verified installation ID on every effect. `runtime/cloudflare-index.ts` has no repository field on runs. `runtime/cloudflare.ts` and `runtime/scheduler.ts` supply reusable DO scheduling, but are **not yet** the live R4 host.
- R4's `worker/main.ts`, `worker/github-connection.ts`, `worker/coder-workspace.ts`, workflows and agents still contain R4-only owners, `main`, issue thresholds and workspace/prompt identities. Rewiring a connector import is useful deduplication, **not** proof of multi-repository operation. Preserve historical `RUNS` records without `revision` before reusing a scheduler namespace.

## Implementation design (decisions for this migration)

### Repository policy and credentials

- The authoritative registry is a **SQLite-backed DO per immutable GitHub repository ID**, not one global DO or the eventually consistent D1 projection. An App webhook includes `repository.id`, `repository.full_name` and `installation.id`; normalize the slug and route directly by repository ID. A legacy repository hook may lack installation metadata, so obtain its installation identity from the trusted App API after signature verification—never invent one from the hook body. The DO stores the expected slug, installation ID, revision, enabled workflows and explicit per-repo policy. A different ID claiming the same slug cannot inherit its enablement. A rename/transfer disables admission until an operator revalidates the actual installation and updates the registry. The projection may list repositories for the UI but must not decide admission or effects.
- The protected admin adapter lists App-installed repositories via a trusted App credential, then creates/updates/disables an individual repository by ID and expected revision (optimistic concurrency). GitHub verification occurs before persisting enablement: fetch the canonical repository/default branch and App installation, and verify the App/token can supply each selected workflow's permissions. A policy has explicit workflow toggles, base branch, issue eligibility and label behavior; unknown fields, unsupported permissions or missing configuration fail closed. Admin writes require a server-verified Access JWT (expected issuer/audience) and explicit operator authorization, with a durable mutation audit; a client-supplied email/header alone is not authority. Never expose the App JWT, installation token or private key to the UI.
- At a minimum, triage needs issue write and content read, feature drafts need content and PR write, and review/check publication needs content read, PR write and (if selected) checks write; use exact per-effect permissions rather than minting a token for all installed repositories. Update `github-app.ts` to return and validate the immutable repository and installation IDs, not just `full_name`. Revalidate policy revision, repository identity, installation and required permission at the trusted credential boundary before each effect. Do not cache a positive policy decision across a run. Disable rejects new starts and new effect requests once acknowledged; already-issued GitHub calls may finish. Scope or retire any cached tokens when policy changes.

### Optional auto-merge capability (disabled by default)

The previous pilot rule was human-only merges. Auto-merge is a **new, separately reviewed capability**, never inferred from enabling triage, prototypes or reviews. A repo policy must opt into a named auto-merge workflow and specify eligible PR ownership, permitted base branch, merge method, required branch-protection checks and human approval requirement. The trusted Worker must verify the current PR head, base and eligibility; completed required checks **on that head**, non-bot human approval, no blocking reviews, and active branch protection that GitHub enforces. Do not treat the bot's own review, its three checks alone, a model verdict, or an unchecked status as sufficient. If branch protection or permissions cannot be inspected, refuse and report blocked. Use GitHub's native auto-merge request so GitHub re-evaluates its gates at merge time; never invoke a direct merge, bypass rule or force-push. Only trusted Worker code has the repo-scoped credential. Reconcile retries and track pending requests; if policy is disabled, cancel outstanding native auto-merge requests before acknowledging it as fully disabled (or report that cancellation is pending/failed). A new PR head must trigger re-evaluation and cancellation rather than inheriting the previous head's decision. Until protection and these cases are tested on an isolated repository, **no live auto-merge or production permission change**.

### Signed ingress and durable identity

- Keep `githubTriggers({ repository })` for existing fixed-repository users. Add a **separate App-wide source** whose graph definitions and trigger IDs do not depend on a configured repository list. Resolve the correct secret from the exact path; bound and verify raw bytes **once for that source**, then parse/validate one authenticated envelope before distributing typed events to matching workflow triggers. Refactor `dispatchWebhook` with an explicit authenticated-envelope/dispatch seam instead of making its current per-trigger `verify` callback an OR of two secrets or trusting a caller-provided repository. Preserve the generic dispatcher for other sources. Do not persist the secret, raw request or installation token in a run.
- The envelope carries canonical slug, immutable repository ID, verified installation ID, action, delivery UUID, digest of the signed raw bytes and the minimal validated issue/PR payload. Reject mismatch among `owner.login`, `name`, `full_name`, numeric ID, issue/PR URL and the enabled registry; reject malformed signatures _before_ JSON parse. Check the enabled workflow before activation. Bad signatures and malformed payloads return 4xx, ignored/disabled actions do not activate, and unavailable policy/claim storage returns a retryable 5xx. A duplicate delivery UUID with changed signed bytes is a conflict. Across repository and App hooks, the same logical event is claimed once even though delivery UUIDs and secrets differ.
- Derive issue claim/queue identities from immutable repository ID + issue number and PR review identities from immutable repository ID + PR number + exact head SHA. Scope all other receipts/agent instance names/workspaces/check external IDs the same way. The new keys must not collide with historical R4 slug-based keys. During any overlap, use **one canonical durable claim owner per logical event**, with an explicit R4 legacy-key lookup/alias or a proven migration—not independent claims for old and new hooks. Keep R4's reopened-issue-joins-original-run behavior for already admitted R4 issues; specify future per-repo reopen policy separately. Commit the event claim before acknowledging, and make starting a claimed run retryable after interruption. A scheduler run receives the validated trigger ID, key and event value, not a naked issue supplied by an HTTP handler.

### Host, effects and history

- The Clankwerk host adapter owns path/host routing, signed dispatch, run creation, alarm delegation, manifest and D1 projection/query APIs. The R4 host registers its workflows/capabilities, admin-only extensions and bindings. Use `cloudflareRunScheduler`/`durableObjectRunStore` in a **new run namespace** while the existing `RUNS` class keeps old records and alarms; route historical run IDs to the old reader. Add repository-aware D1 projection fields via additive migrations; retain old run rows and make missing repository metadata display as legacy/unknown rather than guessing R4. Test a real old record without `revision`, interrupted alarms and definition hashes before any deliberate drain/migration. Do not reinterpret an old record as a new `RunRecord`.
- A validated repository context (numeric ID, slug, installation ID, base branch and policy revision) travels with the run, but effect guards fetch the **current** policy before writes. GitHub connectors receive this context instead of a hard-coded R4 owner/repo/base. Recheck current issue/PR state and exact PR head immediately before publication. Issue #12+, `main`, `r4/issue-*`, `leostera/r4` prompts, workspace names and Bun-specific dependency cache become R4-only policy or repository-aware implementations; unknown test setups yield blocked evidence. The read-only Git gateway must bind to the authenticated repo context and allow only that repository; no GitHub credential enters Pi/Coder. A checked-out repository must match the expected Git remote and selected base, and must not reuse another repository's workspace.
- Maintain a bounded, idempotent D1 projection for repository/workflow run filters; it is never the source of truth for admission or revocation. Use stable source-visible check names only where existing branch protection depends on them; never auto-merge. Register App-wide `issues` and `pull_request` subscriptions only at an explicitly approved cutover (or on a genuinely isolated preview App). Existing R4 repository-hook deliveries continue to work until overlap and rollback tests pass.

## Event identity and compatibility contract

Document and test key semantics **before** switching R4:

- An opened issue is claimed once per repository/issue (including overlapping repository/App hook deliveries); a later reopen currently joins that issue's original run. Clankwerk's existing `githubTriggers.issue` key distinguishes reopened deliveries, so using it as-is would change behavior. Specify whether reopening creates a new run, then deliberately migrate or preserve the current claim.
- An open/reopen/synchronize PR is keyed by repository, PR number and exact 40-byte head SHA; redelivery on that SHA shares a run, a new SHA gets a new run. Delayed old-head runs cannot publish a passing check/review on the new head.
- A changed payload with the **same** delivery ID is a conflict, not a harmless duplicate. Distinct overlapping deliveries for the same logical event must not repeat a feature draft, bot comment, check, or review. Claims and external-write receipts live durably; recheck GitHub after a lost acknowledgement.
- The shared scheduler's stored `RunRecord` has a `revision`; R4's existing `RUNS` records do not. The R4 cutover must preserve historical read access and either drain in-flight old runs or explicitly migrate them. No automatic resubmission or silent status loss. A migration/dual-reader strategy must be proven with real old record fixtures before replacing the `RUNS` class or namespace. Keep old run IDs routable in the dashboard.

## Executable work packages and go/no-go gates

Do these **on matching feature branches only**; package APIs and tests land in Clankwerk before R4 rewires its committed snapshot. Keep `main`, production resources and live hook settings untouched until a separate cutover decision. The earlier table is a summary; these are the ordered change sets:

1. **Contract fixtures and source groundwork (Clankwerk).** Capture redacted old R4 `RUNS`/claim fixtures and test App/repository-hook payloads with two distinct repository IDs, duplicate deliveries, changed-byte reuse, reopen and changed PR heads. Introduce typed authenticated GitHub envelope and explicit source-level verification/dispatch seam in `connectors/github-trigger.ts` and `runtime/webhook.ts`. Preserve fixed-repository `githubTriggers` tests. **Gate:** bad signatures cannot parse/activate; same route verifies only its own secret; signed repo A cannot activate B; old hook and App hook resolve to the same logical claim.
2. **Repository registry and operator surface (Clankwerk package + R4 adapter).** Implement per-repository DO policy storage and conditional enable/update/disable; trusted installation lookup, permission probing and optional D1 read projection. Expose a narrowly scoped admin API behind the existing admin-host/Access boundary; a UI for installed/enabled repos can follow the API but must not become the only enforcement. **Gate:** in a single running build enable installed A then B without deploy; A and B both admit issue #1 independently, disabled/uninstalled/renamed C fails closed; concurrent policy updates conflict; a disable takes effect for later admissions/effects; storage/GitHub outages never turn into consent.
3. **Durable host (Clankwerk package + R4).** Wire the new source to `WorkflowScheduler`, `durableObjectRunStore`, repository-qualified claim/queue and D1 projection. Register repository-independent workflow definitions (with environment-bound source credentials). Keep R4's old `WorkflowRun` and `GitHubDelivery` namespaces accessible while new runs use a separate namespace; adapt agent/feature invocation to carry repository context and trigger metadata. **Gate:** local `cf` Worker/DO signed tests finish triage, feature and exact-head review for two repos; retries, alarm interruption, overlapping hooks and old-run fixtures have no duplicate external effects or lost history.
4. **Scoped effects and agents (Clankwerk package + R4).** Move generic label/comment, archive/Git gateway, draft, review and Check Run reconciliation into connectors accepting the validated context. Replace R4 literals in `worker/github-connection.ts`, `worker/coder-workspace.ts`, `worker/feature-checkout.ts`, agent prompts/idempotency keys and workflow gates with per-repo policy/context. Keep project-specific offline image and conservative test-evidence policy. **Gate:** fake GitHub tests prove one repo cannot read or publish in another; exact-head/base, revoked repo, fork, changed permissions, label absence, lost acknowledgements and bot self-review are handled honestly; no secret enters a container.
5. **Opt-in auto-merge (later gate, Clankwerk + R4).** Add a separately registered workflow/effect for GitHub native auto-merge, with branch-protection, human-approval and exact-head revalidation, durable receipts, revocation/cancellation and no direct merge capability. **Gate:** a protected disposable repo demonstrates successful merge only after real independent required checks and human approval; missing protection, missing review, a changed head, self-review, disabled policy, stale webhook or cancellation failure cannot silently merge. Do not enable on R4 production until branch protection is configured and a separate cutover approves it.
6. **Preview and cutover are separate decisions.** Build/format/typecheck/test both repos, verify the committed package snapshot/digest, and `cf build`. Before **any** preview deploy verify dedicated Worker names, DO namespaces, D1, Access gate, DNS, secrets and an isolated App/hook or no live delivery; default preview GitHub writes to **off** until explicitly allowed for a disposable repo. Only after local parity may an isolated preview be deployed. Production App subscriptions, production hook overlap, rollout of the two existing Workers, historical read routing, monitoring and rollback require an explicit later approval; do not silently replace either production `RUNS` or the demo-ready main tarball.

The branch passes this RFD only after the tests above demonstrate enabling a new installed repository through runtime data **in a running instance**. Merely extracting `fetchExactArchive` or replacing a hard-coded `leostera/r4` constant with another compile-time list is not sufficient.

## Branch implementation checkpoint

The package now has preliminary `github-app-event.ts` (bounded raw-byte signature verification and typed repository-ID decoding), `github-app-source.ts` (repository-independent graph nodes and source-level verification/policy lookup), `github-repository-policy.ts` (revisioned per-repository storage adapter and fail-closed policy checks), and `github-delivery-claim.ts` (transactional duplicate/conflicting-delivery claims). `github-app.ts` can pin token issuance to an immutable repository ID. Unit tests cover two repositories, bad signatures, disabled repositories and replay conflicts. **These are library primitives, not a wired host:** R4 still uses its fixed-repository hook, the new policy/claim DO and protected operator API are not deployed, and no auto-merge code or production permission change exists. Do not mark any of the work-package acceptance gates complete until Worker/DO integration tests prove them.

## Definition of done

A freshly scaffolded Clankwerk project can register a signed GitHub App source, provide one secret binding and a workflow, then **enable a second installed repository via its protected UI/API without editing source or redeploying**. It receives signed events from either repository, durably deduplicates them without cross-repo collisions, and exposes completed runs without a custom parser/scheduler/projection. R4's entrypoint only supplies bindings, policy/capabilities, agent classes, source registry, and optional app-specific admin routes. R4 has no local generic scheduler transitions, raw GitHub HMAC/JSON decoder, duplicate run-index code, or generic GitHub review/check write protocol. Historical R4 runs still resolve; no Worker-per-workflow is introduced. Auto-merge remains unavailable until its separate opt-in, branch-protection and isolated-repository acceptance gate passes.
