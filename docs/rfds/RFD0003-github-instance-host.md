# RFD0003 — A reusable GitHub source and instance host

- Status: Proposed (plan only; no runtime cutover)
- Pilot instance: `leostera/r4` on the existing `r4` and `r4-coder-runtime` Workers
- Related: [RFD0002](RFD0002-clankwerk-cloudflare-native.md), [GitHub workflows](../github-workflows.md)

## Boundary

A Clankwerk project should **declare** GitHub event sources and workflows, supply secret bindings and repository-specific authorization, and deploy one instance Worker. It should not implement another webhook parser, scheduler, run index, retry loop, or GitHub publication protocol. Clankwerk is a _library bundled into that instance Worker_, not a second hosted control plane or one Worker per workflow. The existing GitHub trigger/dispatch/scheduler primitives are a starting point, not yet a plug-and-play host: the template still owns routing and projection, and R4 still runs its own scheduler and admission code.

The host must be composable: non-GitHub/manual/cron sources can share the same runtime. A GitHub plugin must not force every user to install a GitHub App or bundle GitHub secrets in graph manifests. Authenticated event data is still untrusted task input. Host-specific policy remains in host-supplied capabilities or workflow tasks.

## Proposed public seams (illustrative, not final signatures)

1. **Source declaration:** `githubSource({ path, repository, secret: env => env.GITHUB_WEBHOOK_SECRET, events: [...] })` returns typed `issue.opened`, `issue.reopened`, and `pull.opened/reopened/synchronize` graph triggers with deterministic IDs. A secret resolver is called at request time; neither secret nor token enters manifests, logs, persisted events, client bundles, or sandbox tools. Multiple paths/secrets (repository and App hooks) may target one logical source.
2. **Authenticated admission:** an instance-host adapter accepts a trigger-host request, bounds its raw bytes, verifies the correct HMAC before JSON decoding or _any_ activation, validates repository and action, computes a stable key, and durably claims/queues events before responding 202. Invalid/unrecognized deliveries return an explicit 4xx/204; unavailable storage returns 503 for GitHub retry. Shared-path triggers authenticate the request once against the correct path's secret, not one verification per workflow or an OR across unrelated secrets. An unexpected host/path cannot reach admin routes.
3. **Execution:** a Clankwerk-provided run coordinator (`WorkflowScheduler`, `durableObjectRunStore`, and, for partitions, `WorkflowQueue`) owns step transitions, fan-out/join, leases, retries, alarms, and compatible-definition checks. The instance registers workflows and injects environment-bound capabilities; it does **not** copy the phase machine. Keep run DOs and worker routing within the instance's existing Worker. Provide a generic D1 projection/index and read-only dashboard API adapter with optional host routes, so a new instance does not hand-write schema/metrics/runs/source endpoints. HTTP adapter must enforce the admin/trigger hostname split; Access is verified by the instance deployment, never bypassed by a public path.
4. **GitHub effects:** reusable repository-scoped App installation tokens, current-issue reads and reconciled label/comment writes, bounded archives/read-only Git gateway, exact-head PR validation, bounded diffs, idempotent draft/review publication, and individually reconciled Check Runs. `checks:write` is optional and explicit. Verify GitHub's current PR head immediately before every review/check write. A blocked dimension never counts as success. An App bot cannot approve or request changes on its own PR; do not fabricate approval. Publishing has no merge effect. No credential enters a Coder container or Pi tool.
5. **Instance extension points:** repository allowlist, base branch, issue eligibility (#12+ feature policy in R4), model/agent definitions, source-specific workspace, offline dependency strategy, prompts, and human-merge rules stay in R4. Package a Cloudflare sandbox adapter only where it is reusable; R4's Docker image, Bun lockfile cache and concrete application policy are not generic Clankwerk runtime concerns.

Avoid a broad `createApp()` that silently provisions DNS/Access, merges PRs, grants webhook permissions, or guesses a secret. Typed config and explicit capabilities are preferable to a generic `Env`/`any` escape hatch. Preserve the `cf` deployment flow.

## Event identity and compatibility contract

Document and test key semantics **before** switching R4:

- An opened issue is claimed once per repository/issue (including overlapping repository/App hook deliveries); a later reopen currently joins that issue's original run. Clankwerk's existing `githubTriggers.issue` key distinguishes reopened deliveries, so using it as-is would change behavior. Specify whether reopening creates a new run, then deliberately migrate or preserve the current claim.
- An open/reopen/synchronize PR is keyed by repository, PR number and exact 40-byte head SHA; redelivery on that SHA shares a run, a new SHA gets a new run. Delayed old-head runs cannot publish a passing check/review on the new head.
- A changed payload with the **same** delivery ID is a conflict, not a harmless duplicate. Distinct overlapping deliveries for the same logical event must not repeat a feature draft, bot comment, check, or review. Claims and external-write receipts live durably; recheck GitHub after a lost acknowledgement.
- The shared scheduler's stored `RunRecord` has a `revision`; R4's existing `RUNS` records do not. The R4 cutover must preserve historical read access and either drain in-flight old runs or explicitly migrate them. No automatic resubmission or silent status loss. A migration/dual-reader strategy must be proven with real old record fixtures before replacing the `RUNS` class or namespace. Keep old run IDs routable in the dashboard.

## Definition of done

A freshly scaffolded Clankwerk project can register a signed, repository-scoped GitHub source, provide one secret binding and a workflow, receive an authenticated delivery, durably deduplicate it and inspect a completed run without writing a custom parser/scheduler/projection. R4's entrypoint only supplies bindings, policy/capabilities, agent classes, source registry, and optional app-specific admin routes. R4 has no local generic scheduler transitions, raw GitHub HMAC/JSON decoder, duplicate run-index code, or generic GitHub review/check write protocol. Historical R4 runs still resolve; neither Worker-per-workflow nor auto-merge is introduced.
