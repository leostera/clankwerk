# Clankwerk Connect service

Private Bun workspace Cloudflare Worker package; **not an npm publication**. Its shared authorization verifier comes from the local `@leostera/clankwerk` workspace package. Install dependencies at the repository root; the root `bun.lock` covers both workspaces. Target Worker: `clankwerk-connect`; target domain: `clankwerk.leostera.dev`. Deployed with the new `cf` CLI (`bun run build`, `cf deploy`). Public configuration is in `cloudflare.config.ts`; no GitHub credential belongs in that file or the code Sandbox.

## GitHub App setup

- Owner: `@leostera`; App ID: `5213684`; Client ID: `Iv23liqK5uKdioKAUNsp` (these IDs are public).
- User authorization callback: `https://clankwerk.leostera.dev/auth/github/redirect`.
- Webhook delivery URL: `https://clankwerk.leostera.dev/hooks/github`; enable `installation` and `installation_repositories` events for installation lifecycle. Do not enable issue-to-agent or code-write automation.
- For future private repo checkout and approved branch/PR creation, grant **Contents: read/write** and **Pull requests: read/write** for selected repositories only. Metadata read is implicit. Narrow permissions later if read and write can be separated; don't request Administration or Actions/Workflows permissions.
- Rotate any secret shared in a chat or terminal transcript. OAuth now needs a **rotated** `GITHUB_CLIENT_SECRET`, `HANDOFF_ENCRYPTION_KEY` (base64, 32 bytes), and `INSTANCE_REGISTRY` (JSON mapping instance IDs to an exact registered HTTPS `returnTo` and a distinct per-instance signing secret). Webhook verification needs `GITHUB_WEBHOOK_SECRET` set to the same value as GitHub's webhook setting. `r4` is registered through the ignored local `.env`; additional instances must be registered deliberately and receive their own key. The App private key is not needed for this user-to-server OAuth flow. Do not paste secrets in chat, pass them as shell arguments, or put them in tracked files. The ignored, mode-0600 `service/.env` is the operator's local deployment secret file; anyone with access to this computer/account may still read it. Local tests use signed fake events in `src/github-webhook.test.ts`.
- The `cf` CLI requires declared secrets on **first deployment**. Fill the value in `service/.env`, keep that file mode 0600, and run `cf deploy --secrets-file .env` from `service/`. The same value must be configured as the GitHub App webhook secret. For later rotation, update both GitHub and the deployed Worker. A plain `cf deploy` without the secret cannot create the Worker.

## Access and boundary

`clankwerk.leostera.dev` has a self-hosted Cloudflare Access application. The admin root stays behind Access (app `4a9073d3-5887-4e49-ad28-1392f3fd7615`). Two narrower Access applications use reusable Bypass policy `8b22fefc-0739-46cd-9563-d7c7c9aa5e22`: callback `788a6d61-9026-4b3a-8078-392c5b779f93` for `/auth/github/redirect`, and webhook `a3ba3355-e284-4653-a82b-c5b8aa040326` for `/hooks/github`. Cloudflare gives more-specific application paths precedence; these paths also match nested URLs, so **never put admin routes below them**. The Worker accepts only the exact paths and returns 404 for nested URLs. The deployed Worker verifies the webhook secret and only records signed installation metadata. The callback requires one-time, instance-bound state with PKCE and transfers the encrypted credential using a short-lived, single-use ticket. The ticket alone cannot claim a token; the instance Worker must sign its server-to-server request with its own registry key. Do **not** claim GitHub sign-in, private checkout, branch push, or PR creation work from the presence of these URLs alone; an authorized sign-in and instance integration still need end-to-end verification.

Verified on the deployed Worker: unauthenticated `/`, `/settings` and `/internal/start` redirect to Access (302); the callback returns 409 without valid OAuth state; nested callback/webhook paths return 404; a signed `ping` webhook returns 202, unsigned/invalid signatures return 401. Locally a signed instance-start request returned an authorization URL with PKCE. Without the webhook secret even signed requests return 503. No tokens or private keys enter Coder's Sandbox. App installation events are metadata, never proof that a Clankwerk instance is authorized to use that installation: verify the installation and selected repositories against GitHub before any future operation.

## Local checks

Run `bun install --frozen-lockfile` at the repository root. From this directory, run `bun run types`, `bun run typecheck`, `bun run test`, `bun run build`, and `cf deploy --dry-run`. `bun run dev` uses `127.0.0.1:5192` and must not connect to production GitHub until you explicitly provide local test-only secrets. Production installation state is separate from local development state.
